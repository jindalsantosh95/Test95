# Redis subscription scaling

## Objective

Reuse the configured Redis resource to distribute domain events and allow native WebSocket bridge callbacks to land on any GraphQL or Stitch worker. Keep changes uncommitted and leave live Azure configuration unchanged.

## Design

- Native subscriptions always use Redis with an app/environment-specific `NativeWebSocketsRedisPrefix`. Use the existing `RedisCacheConnectionString` through ConfigReader.
- GraphQL uses a version-matched Hot Chocolate Redis event provider. Stitch keeps its remote schema subscription resolvers.
- The owning worker retains the executor and pumps results into bounded Redis mailboxes. Read/stop callbacks authenticate session ownership and connection identity atomically in Redis, independent of callback routing.
- Fixed session expiry, owner heartbeats, bounded buffers and cleanup prevent orphaned subscriptions. Lost owners and Redis outages terminate sessions; clients reconnect and resubscribe. No replay or exactly-once delivery is promised.
- The same Redis implementation supports one or multiple instances/workers; remove the single-instance setting and guard. Disabled native transport retains existing HTTP behavior.
- Preserve callback credential and GraphQL authorization checks. Store owner digests rather than claims or authorization headers in Redis. Prefixes isolate environments, apps and slots.

## Validation plan

Run the existing native transport and Stitch suites plus Redis-backed cross-worker event/read/stop tests, ownership isolation, expiry, namespace isolation and backpressure tests. Use a unique test prefix and never flush the shared Redis resource. Run scoped repository verification before handoff.
