# Behavior Harness

This document defines the executable behavior harness pattern for any solution or project in the repository.

Sequence diagrams and workflow docs describe intended conversations between services, APIs, message brokers, downstream systems, data stores, and external dependencies. By default, sequence diagrams should stay at those service and system boundaries and use actual repository project names for participants; handler-level detail belongs in tests, code references, or an explicitly requested implementation-internals diagram. The behavior harness is the matching feedback layer: every implemented behavior that carries business or integration risk should have a deterministic test or script that proves the contract still holds.

## Required Shape

For every implemented flow:

- keep the detailed sequence diagram or workflow reference current when one exists,
- keep source-of-truth event names, routes, topics, subscriptions, headers, retry rules, and timing rules in code or configuration,
- add focused tests that assert externally visible contracts and important branching behavior,
- add golden fixtures for representative input/output payloads when behavior crosses service boundaries,
- keep deployment and infrastructure coverage enforced by the local harness when the project has deployment artifacts.

For proposed flows:

- label the sequence diagram or workflow as proposed or planned,
- document the expected contract, trigger, integration boundary, and validation approach,
- add executable tests when implementation lands.

## Change Rule

Address Lookup v3 compatible-input coverage in `AddressLookupV3ProviderTests.cs` and `AddressLookupV3SelectionContractTests.cs` proves the public schema exposes `addressLine1`/`postCode`, structured fields map to one downstream suggestions query, mixed input modes fail before dispatch, and existing free-text queries and reference-only container expansion remain supported.

When changing a sequence diagram, workflow, API contract, event subject, subscription, route, configuration key, startup registration, deployment shape, or infrastructure dependency, update the behavior harness in the same change. A diagram-only update is acceptable only when the flow is explicitly marked proposed and there is no implementation yet.

## Operational Enforcement

- `scripts/check-behavior-harness.ps1` requires every `Complete` sequence flow to appear in the Sensor Catalog and requires every catalog sensor path to exist.
- `scripts/invoke-behavior-harness-mutation-exercise.ps1` removes a completed-flow row, breaks a sensor path, and substitutes a placeholder; all mutations must be detected.
- `scripts/check-behavior-harness-strength.ps1 -RequireEvidence` requires a 100% mutation score for the current exercise.
- The mutation exercise runs in every docs verification and in scheduled drift CI. Generated evidence is ignored under `TestResults/behavior-harness/`.
