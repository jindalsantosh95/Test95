# EAPI Response Envelope Translator

**Pattern group:** API Boundary

**Status:** Recommended

**Last reviewed:** 2026-06-01

**Owner:** EAPI Technical Leads

## Intent

Use an EAPI response envelope to separate application outcome from HTTP transport details, then translate that envelope into consistent status codes, headers, security headers, and body serialization at the boundary.

This pattern gives handlers a stable way to express success, validation failure, authorization failure, and technical failure without every endpoint hand-crafting HTTP responses.

## Use When

- Returning a business response from an HTTP-triggered function.
- Mapping application `Status` values to HTTP responses.
- Standardising security headers and error body serialization.

## Do Not Use When

- A service intentionally returns a raw stream or binary response.
- The response is generated by an external framework with its own approved response handling.
- The endpoint is a simple health endpoint using framework health output.

## Pattern Shape

1. Handler returns `Response<T>` or `Result<Response<T>>`.
2. The response carries `Status`, `Value`, optional headers, and optional `Errors`.
3. The boundary helper maps status to HTTP status code.
4. Success bodies and error bodies are serialized consistently.
5. Security headers are applied centrally.

## Implementation Guidance

- Use the response model already established in the owning project.
- Do not duplicate HTTP status mapping in each trigger.
- Put error details in `Errors`, not in success payloads.
- Preserve response headers through the envelope when the API contract requires them.
